# Final author-controlled publication steps
These instructions are prepared only; none of these public actions has been performed.

1. Resolve [the history privacy decision](provenance/PRIVACY_DECISION.md). If choosing a clean-history repository, keep this historical repository private and approve creating the new identity before copying the verified release tree. Do not force-push over the historical repository. If choosing this repository, explicitly approve the historical email exposure.
2. Review RELEASE_AUDIT.md, final candidate commit, source limitations, licenses and release notes. Merge the approved candidate into private main by a non-destructive operation if not already merged. Tag the approved final commit as `v1.0.0` only when ready to release; no tag has been made during preparation.
3. On GitHub open the chosen repository > Settings > General > Danger Zone > Change repository visibility > Public. Confirm the correct repository, read the effects and confirm Make this repository public. History, branches and associated activity become public; inspect those surfaces before proceeding. [Official GitHub instructions](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility).
4. Sign into Zenodo, connect the intended GitHub account (and ORCID), then profile menu > GitHub > Sync now. Find the approved public repository and enable its slider. Enabling ingestion means subsequent releases can be archived automatically. [Official enablement guide](https://help.zenodo.org/docs/github/enable-repository/).
5. Before creating the release, inspect CITATION.cff title, author, ORCID, version and license scope. Use the prepared release notes. Create the GitHub release for the approved `v1.0.0` tag. Wait for Zenodo processing, inspect the resulting record and license/metadata, and verify archived files. [Official archive guide](https://help.zenodo.org/docs/github/archive-software/github-upload/).
6. Copy the DOI actually issued by Zenodo, distinguish the version DOI from the concept DOI, and then update citation/badges/manuscript data availability as appropriate. Do not invent or pre-fill an article DOI or publication date. Metadata corrections after deposit do not change the bytes of an already archived GitHub release; use a new release for content changes.
